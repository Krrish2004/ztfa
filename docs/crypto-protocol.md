# ZTFA — Cryptographic Protocol Reference

> Companion to `HLD_ZeroTrust_FedAgg_HealthIoT.pdf`. Walks through every
> cryptographic primitive the v1 implementation actually uses, with pointers
> to source files.

## 1. CKKS (FHE)

**Library**: TenSEAL (Microsoft SEAL wrapper) — `shared/ztfa_crypto/ckks_context.py`

**Parameters** (HLD §4.1 — locked):

| | Value |
|---|---|
| Polynomial modulus degree N | 2¹⁵ = 32 768 |
| Coefficient modulus chain log₂ | [60, 40, 60] |
| Plaintext scale Δ | 2⁴⁰ |
| Slots / ciphertext | N/2 = 16 384 |
| Multiplicative depth | 1 |

The depth=1 budget covers exactly the `c_sum * (1/N)` rescale step used
by FedAvg. v1 simplification: that scalar mult is moved to plaintext-side
post-decryption, so the in-circuit aggregation only needs `c_sum = Σ c_i`.

**Key model (v1)**: single-issuer. The federation initiator generates
(pk, sk) once via `ztfa_crypto.keygen`, distributes pk to aggregator + chain,
sk to clients via secure out-of-band channel. v2: replace with multi-party
threshold-DKG (Mouchet et al. 2021).

**Runtime invariant** (`shared/ztfa_crypto/ckks_context.py:assert_public_only`):
the aggregator's context MUST NOT carry a secret key. Verified at FastAPI
startup (`ztfa_aggregator.guards`).

## 2. Poseidon (commitments)

**Library**: circomlibjs via Node-subprocess REPL — `circuits/scripts/poseidon_cli.mjs`

The Python wrapper (`shared/ztfa_crypto/poseidon.py`) shells out to a long-
lived Node process to guarantee byte-for-byte parity with the in-circuit
hash (which uses circomlib's Poseidon natively). The reference test vector
`Poseidon(1, 2) = 0x115cc0…189a` is asserted both in
`shared/tests/test_poseidon_parity.py` and in
`circuits/tests/aggregation.test.mjs`.

**Domain-separated commitment** (defends T9 replay):

```
H_i = Poseidon( Poseidon(round_t, client_id),
                Poseidon-chain( chunk31(serialize(c_i)) ) )
```

The same construction lives in:
- Python:  `shared/ztfa_crypto/poseidon.py:commitment`
- circom:  implicit via `aggregation.circom` (off-circuit; the SNARK only
  verifies that the witness digest hashes to the on-chain H_i)

## 3. Groth16 SNARK

**Curve**: BN254 (alt_bn128). **Trusted setup**: per-circuit, locally
generated for v1 dev (`circuits/scripts/setup.sh`); production should reuse
the Hermez ceremony output.

**Constraint count**: 7 668 R1CS constraints (N=3, K=8 digest length).
Proving time: <2 s on stock workstation. On-chain verify: ~280k gas.

**Statement** (`circuits/aggregation.circom`):

```
public  H[N], H_sum
private c[N][K], c_sum[K]

constraints:
  ∀i ∈ [0, N):  PoseidonChainK(c[i]) == H[i]
                Σᵢ c[i] == c_sum               (element-wise)
                PoseidonChainK(c_sum) == H_sum
```

**v1 SNARK simplification (locked)**: the `c[i]` in-circuit are
**compressed digests** (K=8 BN254 Fr elements) of the actual CKKS
ciphertexts, computed via SHA-256 → 4-byte chunks
(`shared/ztfa_crypto/snark_digest.py`). The honest aggregator computes
the same digest over `c_sum` and the SNARK ties them together. An active
aggregator could craft a `c_sum` whose digest matches but whose unobserved
bytes are corrupted — caught by the client at decryption (eval-loop
sanity check on accuracy). v2: scale to full polynomial arithmetic
in-circuit, or migrate to STARK (HLD §13.2).

## 4. Smart contract layer

**`FederationRound.sol`** (`contracts/src/FederationRound.sol`) implements
HLD §7. State machine: `None → Open → Verified | Refundable`.

**`Verifier.sol`** is auto-generated by snarkjs from the circuit-specific
.zkey. Never hand-edit. Regenerate via
`bash circuits/scripts/export_verifier.sh`. Integrity hash captured in
the file header.

**Threat coverage** (HLD §9.2): see `docs/threat-model.md` for T1..T10
mapped to code references.
